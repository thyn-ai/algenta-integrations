# LiteLLM gateway profile-enforcement walkthrough

This page walks one tool profile — `observe` — from the shared contract JSON all the
way to a live call that LiteLLM's MCP Gateway refuses at the proxy. Every shell
command below is executed in CI, so the page cannot silently rot.

The `observe` profile is read-only. A model using it may call `get_contract`,
`query_data`, `simulate`, and `recommend`, but nothing that plans, logs, or executes
decisions. `litellm-algenta` turns that contract rule into a LiteLLM `mcp_servers:`
entry whose `allowed_tools` list is enforced by the gateway itself — not just
filtered at discovery time.

You can follow this walkthrough with no self-hosted Algenta engine and no LLM
provider key. The live section uses the same deterministic stub server and proxy
fixtures as this package's test suite.

Run the commands from `algenta-integrations/python/` with the workspace already
synced:

```bash
uv sync --all-packages --all-extras
```

## 1. Read the profile in the contract

The shared tool-profile contract at the repository root is the single source of
truth for which tools belong to which profile.

```bash
python - <<'PY'
import json
import pathlib

contract = json.loads(
    pathlib.Path("../contracts/integration-tool-contract.json").read_text()
)
print(json.dumps(contract["profiles"]["observe"], indent=2))
PY
```

Expected output:

```json
{
  "default": true,
  "description": "Read-only situational awareness. The default profile for every integration package unless a caller explicitly opts into a higher profile.",
  "tools": ["get_contract", "query_data", "simulate", "recommend"]
}
```

## 2. Generate the YAML that enforces it

`litellm_algenta.config.build_mcp_server_entry` maps that `tools` list onto
LiteLLM's real `allowed_tools` field. Use the bundled CLI to render the YAML
fragment:

```bash
python -m litellm_algenta.config --profile observe --server-name algenta_observe
```

Expected output (trimmed):

```yaml
# Generated by litellm_algenta.config.build_mcp_server_entry ...
mcp_servers:
  algenta_observe:
    url: os.environ/ALGENTA_MCP_URL
    transport: http
    auth_type: bearer_token
    authentication_token: os.environ/ALGENTA_MCP_TOKEN
    allowed_tools:
    - get_contract
    - query_data
    - recommend
    - simulate
    extra_headers:
    - x-trace-id
```

The `url` and `authentication_token` are `os.environ/...` placeholders. LiteLLM
resolves them from the proxy process's environment at startup, so the YAML file
itself never contains a literal endpoint or credential.

## 3. Run the live walkthrough

`examples/profile_enforcement_walkthrough.py` starts a real stub Algenta MCP
server, starts a real `litellm` proxy with the generated config, and drives the
denial end-to-end over HTTP:

```bash
python litellm-algenta/examples/profile_enforcement_walkthrough.py
```

Expected output (trimmed):

```text
litellm-algenta -- profile-enforcement walkthrough (no real engine, no LLM provider key)

== 1. Read the contract's observe profile ==
{
  "default": true,
  ...
}

== 2. Generate observe-profile YAML ==
allowed_tools: ['get_contract', 'query_data', 'recommend', 'simulate']

== 3. Generate execute-profile YAML ==
allowed_params.execute_decision: ['decision_id', 'metadata', 'timeout_seconds', 'webhook_url']

== 4. Start a real LiteLLM proxy with that config ==
Tools visible under the 'observe' profile: ['get_contract', 'query_data', 'recommend', 'simulate']

== 5. Try execute_decision through the observe server ==
HTTP 403 -- refused by the gateway itself (execute_decision is not in allowed_tools)

== 6. Promote to execute profile and try force=True ==
HTTP 403 -- refused by the gateway itself ('force' is not in allowed_params.execute_decision)

== 7. Make a valid execute_decision call ==
ExecutionReceipt: decision_id=walkthrough-delivered, execution_status=delivered, safety_overridden=False

Done.
```

## What just happened

In step 5 the gateway returned a real HTTP `403` because `execute_decision` is
not in `algenta_observe.allowed_tools`. LiteLLM's
`MCPServerManager.check_allowed_or_banned_tools` rejects the call before it ever
reaches the upstream MCP server. That is the difference between a client-side
filter and a gateway-enforced profile boundary.

In step 6 the profile was promoted to `execute`, so `execute_decision` *is*
reachable, but the contract's `never_model_facing_fields` (`force`,
`override_safety`) are still blocked. The generator sets
`allowed_params.execute_decision` to only the model-facing parameters
(`decision_id`, `webhook_url`, `timeout_seconds`, `metadata`), and LiteLLM's
`validate_allowed_params` rejects `force=True` with another real `403`.

In step 7 a call with only the allowed parameters succeeds and returns the typed
`ExecutionReceipt` synchronously — there is no pending or approval-pause state.

## 4. Verify the config with the linter

The same `assert_safe` check the generator runs can be applied to any hand-edited
config. Save the observe fragment to a file:

```bash
python -m litellm_algenta.config \
  --profile observe \
  --server-name algenta_observe \
  --merge-into /tmp/litellm-observe.yaml
```

Then lint it:

```bash
python - <<'PY'
import pathlib
import yaml
from litellm_algenta.config import lint_mcp_server_entry

config = yaml.safe_load(pathlib.Path("/tmp/litellm-observe.yaml").read_text())
violations = lint_mcp_server_entry(config)
print("violations:", violations)
assert not violations, "lint failed"
print("lint passed")
PY
```

Expected output:

```text
violations: []
lint passed
```

## Next steps

Point `ALGENTA_MCP_URL` at your own self-hosted engine's `/mcp` endpoint, set
`ALGENTA_MCP_TOKEN` to its bearer credential, and start the proxy:

```text
export ALGENTA_MCP_URL="http://localhost:8000/mcp"
export ALGENTA_MCP_TOKEN="..."
litellm --config /tmp/litellm-observe.yaml --port 4000
```

This command starts a long-running server, so it is shown as an example and is
not part of the CI-executed sequence above.

See the package [README](../README.md) for the full matrix of profiles, auth
types, trace headers, and token-expiry behavior.
